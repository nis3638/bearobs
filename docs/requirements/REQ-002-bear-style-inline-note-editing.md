# REQ-002 Bear 式笔记原位编辑

## 1. 核心判断

值得做。用户已经在右侧详情栏中阅读目标笔记，点击“编辑”后再弹出一个独立编辑框，只是在复制同一份内容并制造上下文切换。真正需要变化的是详情栏的状态，不是窗口结构。

本需求固定一个交互不变量：

> [!important] 原位编辑不变量
> 阅读态和编辑态必须共用当前笔记详情栏。点击“编辑”只能让原详情栏进入可编辑状态，不能创建独立编辑框、模态窗口、浮层、新窗口或并列的第二编辑区域。

参考 Bear 的范围是原位编辑、视觉连续性和低打扰状态切换；不复制 Bear 的品牌、图标、颜色、文案或像素级布局。

## 2. 目标

- 用户点击“编辑”后，直接在当前笔记显示位置修改内容；
- 保留当前笔记、阅读位置和视觉上下文，避免从阅读界面跳到另一套编辑界面；
- 让阅读态与编辑态尽可能使用同一套布局和内容度量，减少跳动与重新定位；
- 在不改变 Markdown 事实源和安全保存规则的前提下改善编辑体验；
- 为后续实现、自动化测试和回归检查提供明确边界。

## 3. 术语与状态

| 术语 | 定义 |
|---|---|
| 详情栏 | 三栏布局最右侧、用于显示当前选中笔记的区域 |
| 阅读态 | 详情栏展示已渲染笔记，但正文不可直接输入的状态 |
| 编辑态 | 同一详情栏中的标题、正文和受支持内容可直接输入或修改的状态 |
| 原位编辑 | 不替换详情栏、不另开编辑容器，在内容原显示位置进入编辑态 |
| 编辑草稿 | 用户尚未成功持久化的当前修改；它只属于当前笔记，不得串入其他笔记 |

状态转换如下：

| 当前状态 | 用户动作或事件 | 结果状态 | 必须保持的内容 |
|---|---|---|---|
| 阅读态 | 点击“编辑” | 同一详情栏进入编辑态 | 当前笔记、滚动位置、布局上下文 |
| 编辑态 | 输入或修改内容 | 编辑态且存在草稿 | 当前选择、插入点、尚未保存修改 |
| 编辑态 | 执行现有保存动作 | 保存中或编辑态 | 已提交快照与保存期间的新修改均不可丢失 |
| 保存成功 | 继续编辑或回到阅读态 | 同一详情栏中的目标状态 | 最新已保存内容、当前笔记身份 |
| 保存失败 | 查看错误或继续编辑 | 编辑态 | 全部草稿，不得退回旧内容或关闭详情栏 |

## 4. 功能需求

### 4.1 进入编辑态

1. 用户在详情栏点击“编辑”后，当前详情栏必须直接进入编辑态。
2. 系统不得为编辑操作创建 `sheet`、模态窗口、弹出层、新窗口或并列编辑器。
3. 进入编辑态不得改变当前选中的笔记，也不得让笔记列表重新选择条目。
4. 如果可编辑原文仍在加载，加载状态应显示在原详情栏内；加载完成后在同一位置进入编辑态。
5. 如果笔记不可编辑，错误应在原详情栏内说明原因和可执行的下一步，不得弹出一个失去上下文的空编辑框。

### 4.2 编辑表面

1. 标题、正文、列表和任务项应在原显示位置直接可编辑，不得切换成占据另一界面的整篇原始 Markdown 文本框。
2. FR-07 已承诺支持的标题、段落、强调、列表、任务列表、引用、代码和链接，应尽可能保持阅读态与编辑态的结构和排版连续性。
3. 进入编辑态时必须显示明确的插入光标或选择状态，让用户知道输入将落在哪里。
4. 编辑控件不得用额外卡片、边框或大面积背景把正文包装成视觉上独立的“编辑框”；必要的焦点和错误状态除外。
5. 阅读态与编辑态可以显示不同的工具栏动作，但详情栏的内容区域、宽度和层级不得改变。

### 4.3 位置与选择连续性

1. 用户从正文中部进入编辑态时，应保持当前滚动位置，不得跳回笔记顶部。
2. 如果用户在进入编辑态前已有文本选择或明确点击位置，实现可可靠映射时应把插入点放到对应位置；无法可靠映射时，应把焦点放在当前可视区域内，不得默认跳到全文开头。
3. 阅读态与编辑态切换不得造成明显的内容位移、宽度变化或滚动闪烁。
4. 切换到另一篇笔记时，旧笔记的草稿、光标和异步保存结果不得污染新笔记。

### 4.4 保存与错误

1. 原位编辑复用 FR-09 的本地原子保存、索引更新和同步安排，不建立第二套保存路径。
2. 保存成功后，最新内容应继续显示在同一详情栏中；是否继续停留在编辑态由现有保存策略决定，但不得弹出或跳转到另一界面。
3. 保存失败时必须保留用户草稿和编辑焦点，并在当前详情栏中提供可理解、可重试的错误状态。
4. 保存期间发生的新输入不得被较早保存结果覆盖。
5. 离开存在未保存修改的笔记前，必须执行项目统一的保存或离开保护策略；不得静默丢弃草稿。

### 4.5 Markdown 兼容性

1. 原位编辑只改变交互层，保存结果仍为标准 Markdown，Vault 中的 Markdown 文件仍是内容事实源。
2. 未编辑的 Frontmatter、未知语法、空白和换行约定不得被编辑器无关改写。
3. 无法提供结构化原位编辑的语法必须安全降级，并保留原始文本；不得为了维持所见即所得外观而删除或重排未知内容。
4. 任务项勾选、标题层级、列表层级和链接目标在编辑前后必须保持等价语义。

### 4.6 键盘与可访问性

1. 用户可通过键盘触发编辑、在正文中输入并执行现有保存动作。
2. VoiceOver 必须能区分阅读态与编辑态，并读出当前可编辑区域、保存状态和错误信息。
3. 编辑焦点不能只通过颜色表达；浅色和深色模式下都必须可辨认。
4. `Escape`、关闭窗口或切换笔记等离开动作不得绕过未保存修改保护。

## 5. 验收标准

### AC-REQ-002-01 原详情栏进入编辑态

给定用户已在详情栏打开一篇可编辑笔记：

- 点击“编辑”后，原详情栏直接进入编辑态；
- 不出现独立编辑框、`sheet`、模态窗口、浮层、新窗口或第二编辑区域；
- 当前笔记在列表中的选择保持不变。

### AC-REQ-002-02 视觉与位置连续性

给定用户已滚动到一篇长笔记的正文中部：

- 进入编辑态后仍停留在相同内容附近，不跳回顶部；
- 标题、正文宽度和主要块级结构没有明显跳动；
- 插入光标位于当前可视区域，用户可立即输入。

### AC-REQ-002-03 编辑与保存

给定用户在原位编辑态修改标题、段落、列表和任务项：

- 修改过程始终发生在原详情栏；
- 执行现有保存动作后，结果仍在同一详情栏显示；
- 重新打开该笔记时修改仍然存在；
- 本地保存、索引刷新和同步安排继续复用 FR-09 的路径。

### AC-REQ-002-04 保存失败与并发输入

给定保存操作失败，或保存期间用户继续输入：

- 保存失败不会关闭编辑态或清空草稿；
- 错误在当前详情栏中可见并可重试；
- 较早保存操作完成后，不会覆盖保存期间产生的新修改；
- 切换笔记后，旧保存结果不会写入新笔记界面。

### AC-REQ-002-05 Markdown 保真

给定笔记包含 Frontmatter、不同换行风格、受支持格式和未知 Obsidian 语法：

- 只修改一个普通段落并保存后，目标段落按预期变化；
- 未编辑 Frontmatter、未知语法和换行约定不被无关改写；
- 重新读取后的标题、列表、任务项和链接语义与保存前未编辑部分一致。

### AC-REQ-002-06 可访问性与键盘

- 键盘可触发编辑、定位正文并执行现有保存动作；
- VoiceOver 可识别编辑态、可编辑区域、保存状态和错误状态；
- 浅色与深色模式下，编辑焦点和错误状态均不只依赖颜色表达。

## 6. 兼容性与迁移约束

- 现有 `EditorFeatureModel` 的加载、草稿、保存和并发保护语义应继续复用；本需求主要改变编辑容器和阅读/编辑状态组合方式。
- 移除独立编辑 `sheet` 时，不得削弱现有保存失败、重试、离开保护和可访问性能力。
- 现有 Reader、笔记列表和路由继续使用同一笔记身份，不能为原位编辑引入第二份脱离当前选择的文档状态。
- 本需求不得改变 Vault 路径、索引身份、同步基线或 WebDAV 冲突规则。

## 7. 非目标

- 不要求复制 Bear 的品牌、图标、颜色、文案或像素级视觉；
- 不承诺一次覆盖全部 Obsidian 语法和插件语法的高级富文本编辑；
- 不在本需求中增加笔记创建、删除、重命名或多人协作；
- 不在本需求中改变 Markdown 文件格式、同步协议或冲突策略；
- 不额外规定自动保存节流时间等实现参数，保存行为继续服从 FR-09 及后续技术设计。

## 8. 实现收口待办

以下事项全部完成并通过对应验收前，REQ-002 不得标记为“完成”：

- [ ] 为 Markdown 节点建立精确的 UTF-8 半开源码区间，支持阅读节点、编辑节点与原始字节的可靠映射；
- [ ] 建立结构化编辑节点与未知 Obsidian 语法不透明节点，使两类节点可以在同一编辑树中共存；
- [ ] 将结构化修改转换为针对基线源码区间的最小源码补丁，并复用现有原子保存路径；
- [ ] 实现阅读态到编辑态的滚动位置、点击位置、选择和光标恢复，避免切换时跳回顶部或产生明显位移；
- [ ] 补齐 macOS UI 验收，覆盖原位编辑、滚动与焦点连续性、保存失败、并发输入、切换笔记保护、键盘和 VoiceOver。
